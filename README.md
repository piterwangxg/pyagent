# pyagent

这个仓库是我对 agent 的理解，以及一个准备真做出来的 agent 项目。

我个人觉得 agent 现在大致分两类。一类是工作流的形式，大模型用固定工具，按明确的步骤把任务走完，代表有 Dify 这类低代码编排平台。另一类是大模型自己选工具、自己看返回结果、再决定下一步，代表有 OpenClaw、Codex。

以前我容易把它俩当成新旧两个阶段，现在不这么看了。真正的区别是控制流写在哪：写死在代码里，还是运行时交给模型决定。这两件事可以同时存在，所以它更像一根光谱，而不是两个坑。中间还有不少形态，比如让模型只做一次路由，或者模型负责拆任务、子任务走固定流程，或者循环结构固定、只让模型负责写和评。实际系统大多落在中间，两头反而是少数。

工作流在企业里见得多，尤其是金融、审批、数据加工这些要求可追溯可审计的场景。但我觉得原因不是"工作流更稳"，而是它的路径就摆在代码里，能进版本库、能写单测、出了问题能一行行看。agent 的路径是运行时生成的，事后只能翻 trace 还原。所以企业里真正要保住的是关键节点的控制权，而不是工作流这个形式本身。落成一句话：金额、权限、审批这类不可逆的事必须留在代码里，模型只做分类、抽取、给建议。

这两类我觉得是相辅相成的，外层工作流保证边界和合规，内部节点让 agent 做动态决策，这样比较符合我理解的 agent 工程形态。工作流这块就不展开了，用 LangChain 也好、用 Dify 也好，都能比较高效地搭出来。

`agent = harness + 大模型` 这个说法我认。不过 harness 目前没有统一的定义。

harness 大概就是模型外面那一层运行时，管上下文、工具、循环、权限、日志、评估这些。我原来只写了"约束、反馈、验证"，后来觉得最该强调的是验证。因为 agent loop 说白了就是生成、执行、看结果、改，如果"看结果"这一步没有能被自动判定的信号，模型看到的东西就没什么信息量，循环很容易变成反复瞎试，越试越贵。这也顺带解释了为什么写代码的 agent 最先成熟，编译器和测试就在那儿摆着，错了立刻知道。金融审批没有这么干脆的判定器，只能靠人审和工作流兜底。

所以我现在更愿意这么写：一个 agent 的上限，大概等于模型能力乘上上下文质量，再乘上验证强度。harness 干的所有事，无非是让模型犯的错能被发现，还能被它自己改回来。
